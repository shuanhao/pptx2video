# 事件報告：相鄰字幕時間戳重疊，導致燒字幕時整句「消失」

- **發現日期**：2026-08（測試燒字幕功能、對照真實 MCU 課程影片時發現）
- **影響範圍**：`src/subtitle_alignment.py` 的 `align_segments_with_word_boundaries()`——這是產生 `.srt` 時間戳的核心函式，任何用這個專案產生的字幕都可能踩到；`scripts/burn_subtitles.py`（燒字幕）是讓這個問題從「肉眼幾乎看不出來」變成「整句話消失」的放大鏡，但問題本身不是燒字幕造成的。
- **嚴重程度**：中高——不會影響音訊或畫面本身，但會讓觀眾漏看一整句字幕內容，而且原本的軟字幕（`.srt`）在一般播放器上通常不會有明顯異狀，容易被忽略，直到燒字幕才會被看見。
- **狀態**：已修復，已通過合成測試案例驗證，並已在真實完整 deck 上重新產生 `.srt` 後完成最終確認（見第 8 節）。

---

## 1. 使用者怎麼發現的

使用者測試「切分段 + 燒字幕」功能時，比對其中一段燒好字幕的影片，發現原始 `.srt` 裡的第 106 句「的『眼睛』與『耳朵』」沒有出現在畫面上。使用者附上了那一段 `.srt` 的原始內容：

```
105
00:05:06,626 --> 00:05:09,598
所以我們可以說，Sensor 提供的是系統

106
00:05:09,181 --> 00:05:11,990
的「眼睛」與「耳朵」
```

## 2. 第一層線索：兩句字幕的時間戳本身重疊

仔細看這兩句的時間戳：第 106 句的開始時間 `00:05:09,181` **比第 105 句的結束時間 `00:05:09,598` 還早 0.417 秒**。也就是說，這兩句字幕本來就有一段時間是同時「應該顯示」的——這不是燒字幕或切分段造成的，這兩個時間戳在原始的 `.srt` 檔案裡就已經是這樣。

## 3. 用重現測試找出「消失」的真正機制

為了確認這個重疊時間戳跟「畫面上完全看不到那句話」之間的因果關係，用完全相同的時間戳燒進一段合成測試影片重現：

```
105  00:00:06,626 --> 00:00:09,598  所以我們可以說，Sensor 提供的是系統
106  00:00:09,181 --> 00:00:11,990  的「眼睛」與「耳朵」
```

擷取兩個時間點的畫面：

- **9.3 秒**（兩句重疊的時間窗內）：兩句字幕**都有畫出來**，但 106 被 libass 的碰撞迴避機制自動往上推，跑到我們畫的固定黑條**外面**，疊在原始畫面（測試用的是藍色背景）上，沒有黑底。
- **10.5 秒**（105 已經結束、只剩 106）：106 恢復正常顯示在黑條裡。

**結論**：106 這句話並沒有真的「消失」或被 ffmpeg／libass 丟棄——它有被畫出來，只是在兩句重疊的那 0.417 秒內，被自動推到黑條保護範圍之外。在真實課程影片裡，那個位置通常是投影片的白色/淺色背景，白色字疊上去幾乎看不見，這才是使用者看起來「這句沒出現」的真正原因。

## 4. 根本原因：字幕產生階段的時間計算 bug

追到 `src/subtitle_alignment.py` 的 `align_segments_with_word_boundaries()`。這個函式替每一句字幕算時間的邏輯，是把 edge-tts 回報的每個「WordBoundary 事件」（它自己切詞的最小單位），依照文字的字元位置分配給對應的那句字幕：

```python
overlapping = [
    m for m in matched
    if m["source_start_offset"] < seg_end_off and m["source_end_offset"] > seg_start_off
]
if overlapping:
    start_seconds = min(m["offset_seconds"] for m in overlapping)
    end_seconds = max(m["offset_seconds"] + m["duration_seconds"] for m in overlapping)
```

問題出在：如果字幕斷句演算法（`subtitle_segmenter.py`）把一整句話從中間斷成兩行字幕的地方，剛好落在 edge-tts 某一個 WordBoundary 事件的文字範圍**中間**（例如「系統的」被 TTS 當成同一個詞的一部分，但字幕斷句演算法因為行寬限制，把「系統」留在上一行、「的」放到下一行），這一個事件的字元範圍會同時「跨」到兩句字幕的範圍裡，被两句字幕都算進自己的時間——前一句的結束時間因此被拉晚（因為它把這個共用事件的完整結束時間也算進去），後一句的開始時間卻同時被拉早（因為它把同一個事件的開始時間也算進去）。兩句字幕的時間戳就這樣產生了不該有的重疊。

用一個最小的合成案例重現這個機制（不需要真實 TTS 資料）：

```python
text = "ABCDEF"
segments = [
    {"text": "ABC", "source_start_offset": 0, "source_end_offset": 3},
    {"text": "DEF", "source_start_offset": 3, "source_end_offset": 6},
]
word_boundaries = [
    {"text": "AB", "offset_seconds": 0.0, "duration_seconds": 0.2},  # 完全在第一句內
    {"text": "CD", "offset_seconds": 0.3, "duration_seconds": 0.2},  # 跨在斷句點正中間（字元位置 2-4）
    {"text": "EF", "offset_seconds": 0.7, "duration_seconds": 0.2},  # 完全在第二句內
]
```

修正前的結果：

```
第一句: start=0.0, end=0.5   （因為算進了 "CD" 的結束時間 0.3+0.2=0.5）
第二句: start=0.3, end=0.9   （因為算進了 "CD" 的開始時間 0.3）
```

第二句在 0.3 秒就開始了，但第一句要到 0.5 秒才結束——重疊 0.2 秒，跟真實案例的結構完全一致。

## 5. 修法

在 `align_segments_with_word_boundaries()` 算完每句原始時間之後，原本就有一個「把結束時間往後延伸到下一句開始前」的收尾迴圈（用來填補句子之間的自然停頓，避免字幕一閃一閃）；這次在同一個迴圈裡加了另一個分支：如果某句字幕的結束時間已經超過下一句的開始時間（重疊，而不是單純的停頓不夠長），就把它的結束時間**收斂**到下一句開始的時間點，並且用這句自己的開始時間當下限，避免萬一重疊嚴重到讓收斂後的結束時間還比開始時間早（產生負時長的畸形區間）。

```python
elif aligned[index]["end_seconds"] > next_start:
    aligned[index]["end_seconds"] = max(next_start, aligned[index]["start_seconds"])
```

修正後同一個合成案例的結果：

```
第一句: start=0.0, end=0.3
第二句: start=0.3, end=0.9
```

不再重疊，任何時候畫面上最多只有一句字幕。

## 6. 驗證

新增了兩個測試（`tests/test_subtitle_alignment.py`）：

- `test_straddling_word_boundary_event_does_not_overlap_adjacent_segments`：完整重現上述「跨斷句點的 WordBoundary 事件」情境，驗證修正後兩句字幕的時間不再重疊。
- `test_clamping_never_inverts_a_segment_into_negative_duration`：驗證即使重疊嚴重到收斂會產生負時長，也會正確地被限制在這句自己的開始時間，不會產生結束時間早於開始時間的畸形資料。

全部 190 個測試（含這 2 個新增的）通過。

## 7. 適用範圍

這個修正改的是 `.srt` 產生邏輯本身，不是燒字幕功能——換句話說，**軟字幕（一般播放器看到的 `.srt`）跟硬字幕（燒進畫面）都會受惠於這次修正**，不只是燒字幕情境。要讓已經產出的 `deck.mp4` 套用這個修正，需要重新執行 `scripts/regenerate_srt_from_export.py` 產生新的 `captions.srt`；如果之前有切過分段，`split_video_by_slides.py --subtitles`（要的話再加 `--burn-subtitles`）也要重新跑一次。

## 8. 真實完整 deck 上的最終確認

使用者用 `scripts/regenerate_srt_from_export.py` 針對真實課程 deck 重新產生了 `captions_v2.srt`，並提供新舊兩版完整 `.srt`（各 3,360 條字幕）供比對。逐條掃描兩份檔案裡「前一句結束時間 > 下一句開始時間」的重疊情形，結果：

| 檔案 | 總 cue 數 | 重疊數 |
| --- | --- | --- |
| 舊版 `captions.srt` | 3,360 | 6 |
| 新版 `captions_v2.srt` | 3,360 | 0 |

舊版裡的 6 處重疊分別是第 105/106、164/165、241/242、520/521、1235/1236、2169/2170 句，重疊量落在 0.42～0.54 秒之間；新版裡這 6 處全部被修正——每一處前一句的結束時間都被夾（clamp）到剛好等於下一句的開始時間（例如 105 句結束時間從 `09,598` 變成 `09,181`，正好等於 106 句的開始時間），且沒有引入任何新的重疊。全份 deck 掃描確認：**修正後 0 處遺漏、0 處新增**。

## 9. 根因的進一步佐證：edge-tts 把多字詞合併成單一事件

為了確認「WordBoundary 事件跨在字幕斷句點上」這個根因不是單一巧合，額外用同一批語料裡的逐字時間軸（`*.wordboundaries.json`）直接查證，確實找到 edge-tts 把多個中文字合併成**同一個**事件、而非一字一事件的實例，例如：

```
{'text': '系統的', 'offset_seconds': 199.09, 'duration_seconds': 0.458}
{'text': '廣泛',   'offset_seconds': 443.42, 'duration_seconds': 0.375}
```

這兩個合併事件的長度（0.458 秒、0.375 秒），跟真實重疊案例觀察到的重疊量（0.42～0.54 秒）在量級上吻合，佐證了第 4 節的根因推論：只要字幕斷句點剛好切在這種合併事件的文字範圍中間，前後兩句字幕就會同時把這個事件的時間算進自己身上，產生重疊。

## 10. 相關但獨立的問題：斷詞造成的硬斷字（尚未處理）

在追查第 164/165 句（「...為什麼會廣」／「泛出現在各種電子產品中」）時，額外發現一個**與時間軸重疊無關、但成因相關**的問題：字幕文字本身把「廣泛」這個詞從中間拆開，分別放在兩行。

原因出在 `subtitle_segmenter.py` 的 `_hard_split()`——當一段話超過行寬上限、又沒有標點可斷時，這個函式改用 jieba（中文斷詞工具）在詞與詞的邊界之間切，理論上不會切斷一個完整的詞。但實測發現 jieba 對這句話本身的斷詞就是錯的：

```
理解 MCU 為什麼會廣泛出現在各種電子產品中
→ ['理解', ' ', 'MCU', ' ', '為', '什麼', '會廣', '泛出', '現在', ...]
```

jieba 把「會廣泛出現」誤判成「會廣」＋「泛出」＋「現在」，而不是正確的「會」＋「廣泛」＋「出現」＋「在」。`_hard_split()` 忠實地只在 jieba 給出的詞界切，但 jieba 本身給錯了詞界，所以「廣」「泛」被分進不同的 token，最終落到兩行不同的字幕——這純粹是文字斷行問題，跟第 4～6 節描述的時間軸重疊機制是兩條獨立的成因鏈，只是剛好在 164/165 這個位置同時發生（因為 edge-tts 把「廣泛」也視為單一 WordBoundary 事件，所以這裡的斷行點同時踩中了「跨事件重疊」跟「跨詞硬斷」兩個問題）。

這個問題目前**尚未修正**（使用者決定另外處理），單純記錄在這裡供之後參考。可能的改善方向：替 jieba 載入自訂詞典加強常見雙字詞的辨識、或在斷行前對已知常見詞做一個小型保護清單，避免類似「廣泛」這種詞被跨行拆開。
