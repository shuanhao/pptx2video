# 匯出用音訊準備功能整合評估

> 設計更新：音訊準備已改為同層固定檔名、每次全部重轉，移除 `--force-prepare-audio` 與快取重用。以下關於版本化、整批回復與重用的敘述保留為歷史紀錄；現行規則見 [音訊準備手冊](AUDIO_PREPARATION.md)。舊驗收結果不等同新版已通過驗收。


- 日期：2026-09-30
- 狀態：設計評估，尚未實作。
- 目標：將目前手動執行的「音訊轉換、尾端補靜音、建立衍生 manifest」整合進專案，最大程度沿用既有 CLI。
- 本次僅更新評估與計畫，不代表已修改 Python 程式、新增參數或完成測試。
- 依據：現有文件、先前核對的主流程與字幕相關程式碼，以及使用者在本機 PowerPoint 完成的對照實驗。實驗觀察不等於已確認所有環境的通用行為。

## 1. 需求與建議結論

希望最終 MP4 每個配音頁在原始音檔播放完成後，再保留約 3～5 秒才換頁；目前以 4 秒為主要測試設定。

建議新增可選的「匯出用音訊準備階段」，位於 TTS 完成之後、插入 PowerPoint 之前。原始 MP3 與 WordBoundary 保留，另行產生供插入、定位與字幕流程使用的 M4A 或 WAV，以及獨立 manifest。

```text
第一階段：解析原始 PPTX
→ 生成或讀取原始 TTS 音訊
→ 選用：轉 M4A／WAV、尾端補靜音
→ 決定本次實際使用的 manifest 與音訊目錄
→ 產生 captions_preview.srt
→ 插入 PPTX
→ 匯出 MP4
→ 產生 captions_initial.srt 與 captions.srt
→ 結束第一階段

人工播放影片，比對並選定與語音同步的字幕

第二階段：明確指定 MP4 與選定的 SRT
→ 讀取影片實際解析度，自動套用 720p／1080p 黑條尺寸
→ 燒字幕，輸出另一份 MP4
```

音訊補秒未啟用時維持原音訊流程。第一階段可從原始 PPTX 一路執行到 MP4 與三份候選字幕，也能先生成 TTS、稍後轉換，再獨立插入與匯出。第一階段完成後程式正常結束，不自動選字幕或接續燒錄；使用者人工確認後才另外執行第二階段，不需要新增互動等待或確認開關。

依本次討論，取消獨立的 `--prepare-audio` 開關，統一由 `--audio-tail-silence` 控制：預設 `0` 完全沿用原流程；設定為 `1～10` 秒才啟用補秒及格式轉換。第一版不提供「0 秒、只轉格式」模式。

第一版建議以 AAC-LC／M4A 為預設衍生格式，PCM WAV 為對照或替代選項，不優先提供 MP3 重新編碼。不要將 `1.001221` 寫入新功能的預設值；既有校正係數仍維持 `1.0`。

## 2. 已取得的實驗證據

### 2.1 MP3 重新編碼與 PowerPoint 匯出異常

使用者以同一頁音訊替換後匯出，觀察到以下結果：

| 插入音訊 | 匯出觀察 |
|---|---|
| 原始 Edge-TTS MP3 | 正常 |
| 重新編碼 MP3，沒有補靜音 | 固定位置缺字、停頓 |
| 重新編碼 MP3，尾端補 4 秒 | 同一位置缺字、停頓 |
| 原始 MP3 解碼為 PCM WAV，補 4 秒 | 測試頁正常 |
| 原始 MP3 轉 AAC／M4A，補 4 秒 | 測試頁目前觀察正常 |

重新編碼 MP3 在 PPTX 內直接播放正常，但 MP4 與從 MP4 抽出的 WAV 都缺少相同發音。因此支持「重新編碼 MP3 與 PowerPoint 匯出管線的相容性問題」，而非 VLC 播放顯示或字幕造成。

仍未定位到特定 MP3 標頭、編碼器延遲或影格結構，不能把推測寫成已確認根因。未補靜音的重新編碼 MP3 也會觸發問題，表示新增靜音不是必要觸發條件。

### 2.2 格式與容量取捨

本機 Edge-TTS 套件要求的音訊格式為 MP3、CBR 48 kbps、24 kHz、單聲道。先前使用 `libmp3lame -q:a 2` 的處理引入 VBR，VLC 滑桿在尾端靜音處不平滑；CBR 對照改善了進度顯示，但沒有解決 PowerPoint 匯出缺音。

目前已測試的替代格式：

- M4A：AAC-LC、目標 64 kbps、24 kHz、單聲道。
- WAV：PCM 16-bit、24 kHz、單聲道，資料率約 384 kbps。

以 2 小時 40 分鐘計算，48 kbps MP3 約 57.6 MB、64 kbps AAC 約 76.8 MB、PCM WAV 約 460.8 MB，皆為不含補秒與封裝開銷的概算。AAC 實際平均位元率可略有不同。

WAV 增加音訊與 PPTX 容量，MP4 不會因輸入改用 WAV 而必然同比例變大。Microsoft 建議 PowerPoint 使用 AAC 編碼的 M4A，但官方支援不等於已驗證本專案所有匯出情境。

### 2.3 大型簡報與比例校準觀察

使用者提供的最後一句字幕時間如下：

| 字幕 | 最後一句開始 |
|---|---|
| 原始 MP3 預測版 `captions_preview.srt` | 02:41:40,014 |
| M4A 匯出後實測版 `captions_initial.srt` | 02:43:14,174 |
| 再套用 `1.001221` 的 `captions.srt` | 02:43:26,133 |

實際影片最後一句約在 02:43:14 開始，支持這次使用 initial、係數 1.0；额外校準反而造成約 12 秒延後。

這不證明 M4A 已修復所有歷史比例偏差，因為格式、重新編碼及尾端靜音同時改變。也不能只憑最後一句推論所有頁面都同步。正式驗收仍需抽查前、中、後段與長頁面的頁首、頁尾。

## 3. CLI 介面提案

以下參數均尚未存在：

| 參數 | 建議預設 | 用途 |
|---|---|---|
| `--audio-tail-silence` | `0` | 唯一啟用條件：0 關閉；1～10 秒啟用尾端補靜音與轉換 |
| `--prepared-audio-dir` | `output/audio_prepared` | 啟用時的衍生音訊與 manifest 輸出位置，不是原始檔備份目錄 |
| `--prepared-audio-format` | `m4a` | 啟用時支援 `m4a`、`wav` |
| `--prepared-audio-bitrate` | M4A 為 `64k` | AAC 目標位元率 |
| `--prepared-audio-sample-rate` | `24000` | 衍生音訊取樣率 |
| `--prepared-audio-channels` | `1` | 衍生音訊聲道數 |
| `--force-prepare-audio` | 關閉 | 略過可重用判定、強制重新生成衍生音訊 |

### 3.1 必須明確的語意

- `--audio-output-dir` 仍指原始 TTS 目錄，不改變舊參數的意義。
- 設定非零補秒不要求同時使用 `--generate-audio`，可讀取既有原始 TTS manifest。
- 補秒為 0 時不執行轉換、不建立 prepared 目錄、不因本功能新增 ffmpeg／ffprobe 檢查；原流程自身需要的工具檢查仍照常執行。
- 補秒為 0，卻明確指定任一 `--prepared-audio-*` 參數或 `--force-prepare-audio`，應報錯而不是靜默忽略。實作時須區別預設值與使用者明確傳入的值，先判斷啟用與衝突，再補上啟用時的預設設定。
- 補秒允許 0 或 1～10 的有限數值；拒絕 NaN、Infinity、負值、介於 0 與 1 之間及超過 10 的值。範圍內可接受小數秒，例如 1.5；0 不轉格式。
- 補秒定義為「原始檔案結尾再追加」，不自動裁切原有靜音，也不是「最後發聲後總共停留指定秒數」。
- WAV 使用 PCM 16-bit，不接受使用者明確指定 AAC bitrate；M4A 預設 bitrate 不應導致 WAV 預設呼叫誤報錯。
- 啟用時檢查 ffmpeg／ffprobe 是否存在；來源與輸出目錄須分離，不允許解析後同一路徑或互相包含，避免覆寫與來源混用。
- 保留既有 `--video-default-duration` 作為無旁白頁政策，不對無旁白頁另外追加音訊尾端秒數。
- 保留 `--global-scale-correction`，不依格式自動套用經驗值。

### 3.2 部分頁面重生

維持 `--slides` 原本限定 TTS 重生頁面的語意。準備階段讀取合併後的完整 manifest，逐頁判斷來源、設定與產物是否一致，只轉換需要更新的項目。

如此不需要第一版就新增另一組頁碼選擇器，也不會因只重生第 6 頁而讓其他頁消失。若全域格式或補秒改變，所有受影響頁面都應重建。

## 4. 新增模組與函式

建議新增 `src/audio_preparation.py`，不將 ffmpeg 後處理塞進 `tts.py`。

| 名稱 | 建議責任 |
|---|---|
| `AudioPreparationOptions` | 保存格式、補秒、位元率、取樣率與聲道設定 |
| `validate_preparation_options()` | 驗證 0／1～10 秒、明確參數衝突與路徑安全；關閉時不觸發準備工作 |
| `probe_audio()` | 取得 codec、取樣率、聲道與時長，必要時補充解碼後長度 |
| `prepare_audio_file()` | 從一份原始音訊生成並驗證衍生音訊 |
| `prepare_audio_manifest()` | 依 manifest 批次轉換、處理 WordBoundary 副本並提交新 manifest |
| `is_prepared_entry_current()` | 判定來源、設定、工具資訊與輸出是否可重用 |

`prepare_audio_file()` 的必要步驟：

1. 確認來源是原始音訊，不把 prepared 產物再次補秒。
2. 以 argv 陣列呼叫 ffmpeg，避免自行拼接 shell 命令。
3. 使用有正確格式副檔名的暫存輸出。
4. 檢查 exit code、檔案非空、可解碼、格式與時長是否合理。
5. 成功後才提交產物；失敗保留前一份有效結果。
6. 回報頁碼、來源及 ffmpeg 錯誤，供 CLI 統一處理。

AAC 容器長度可能包含編碼與封裝影響，不能要求所有量測方式都精確相差 4.000 秒。驗收容許值需由合成測試與實際解碼結果決定。

`prepare_audio_manifest()` 應回傳 manifest、實際音訊目錄及處理摘要，例如轉換／重用的頁碼。TTS 成功但轉換失敗時，應停止後續插入，原始 TTS 產物仍可供重試使用。

## 5. Manifest 與產物生命週期

`--audio-output-dir` 保存原始 MP3、WordBoundary 與原始 manifest；`--prepared-audio-dir` 保存補秒後的 M4A／WAV、供既有讀取方式使用的 WordBoundary 副本及衍生 manifest。原始資料留在原處，不搬到 `original` 目錄，也不另複製一份 MP3 作備份。兩個目錄分別表示來源與衍生結果。

只有非零補秒才使用衍生輸出設定。切回 0 不刪除既有 prepared 產物，但也不會自動選用它們。

### 5.1 保留既有讀取欄位

衍生 manifest 保留既有欄位，使現有插入與字幕工具可讀取：

```json
{
  "output_dir": ".../output/audio_prepared",
  "slides": [
    {
      "slide_num": 2,
      "audio_file": "slide_002.m4a",
      "word_boundaries_file": "slide_002.wordboundaries.json"
    }
  ]
}
```

上例為概念結構；若採版本化產物，檔名或相對子路徑可包含生成識別碼。消費端只需遵循 manifest，不依賴固定檔名。

### 5.2 新增可選 metadata

- Schema 版本與 prepared 產物類型。
- 原始音訊及 WordBoundary 雜湊。
- 原始檔案對照資訊。
- 編碼、補秒、取樣率、聲道與工具版本。
- 原始與衍生音訊量測時長。
- 生成識別碼與本頁處理結果。

原始 TTS manifest 不被覆寫。WordBoundary 保留原始時間，不人工增加尾端事件；是否能完全沿用仍須以 AAC 轉碼後時間對齊測試確認。

舊版無 metadata 的原始 manifest 仍可作為來源。歷史上已被手動補秒卻沒有標记的檔案，不能靠程式自動辨識其來源；這類舊資料需要使用者明確提供乾淨來源。

### 5.3 重跑與安全提交

不能只比較檔名或修改時間。來源 MP3、WordBoundary、轉換設定或已提交產物變更時，需重新處理或明確報錯。

同一來源與設定重跑，不應再增加 4 秒；強制重跑也必須從原始檔開始。

多檔更新不能只靠「最後寫 manifest」保證安全：若先覆寫舊 manifest 引用的音訊，後面失敗仍會造成混批次。建議使用版本化檔名／目錄，全部完成後原子替換 manifest，確保舊 manifest 仍指向完整舊資料。自動清理舊產物不列入第一版，避免破壞可回復性。

## 6. 主流程的修改重點

`src/main.py` 目前在插入、字幕與 payload 組裝多處直接使用 `args.audio_output_dir` 及 `_resolve_audio_manifest()`。

新階段應放在「TTS 部分頁面 manifest 合併完成」之後、「建立 payload 與預測字幕」之前，統一建立：

```text
effective_manifest
effective_audio_dir
```

補秒為 0 時，兩者指向使用者指定的原始音訊；為 1～10 時，指向本次已驗證或重建的衍生音訊。不得因 prepared 目錄存在就自動啟用。以下呼叫都必須使用相同的一組：

- `build_payload()`。
- 預測字幕產生。
- `ppt_automation.insert_audio()`。
- 匯出後音訊定位與字幕生成。

這是最重要的整合點。只改插入端、字幕仍量測原始長度，會讓新增停留時間漏算到後續搜尋位置。

生成、插入與匯出仍可分開執行。新功能的分階段操作持續以 `--audio-output-dir output/audio` 指向原始來源，並傳入相同的 `--audio-tail-silence 4` 及轉換設定；準備階段驗證後重用衍生產物，不重新呼叫 TTS，也不累加靜音。不得將 prepared manifest 當作再次補秒的來源。

對已含音訊的 PPTX 單獨匯出時，補秒參數不會修改其中的嵌入媒體；定位與字幕使用的 manifest 必須對應該 PPTX 實際插入的音訊。改變補秒或格式後，須從乾淨原始 PPTX 重新插入再匯出。

### 6.1 第一階段的三份候選字幕

以下是本次新增的輸出規劃，不代表目前 CLI 已會同時保留三份字幕：

| 產物 | 產生時點與相依性 | 用途 |
|---|---|---|
| `captions_preview.srt` | 匯出前，使用 effective manifest、實際音訊長度、原始 WordBoundary 與既有無旁白頁時長規則 | 預測版；啟用補秒時，後續頁面 offset 必須包含新增靜音 |
| `captions_initial.srt` | 匯出後，使用 MP4、相同 effective 音訊與 WordBoundary 定位，額外全域校正係數固定為 1.0 | 保留未套用額外全域校正的實測對齊基準；仍包含既有頁內時間映射 |
| `captions.srt` | 使用同一批定位結果與文字資料，依指定的全域校正係數輸出 | 校正候選版；係數為 1.0 時內容應與 initial 一致 |

preview 的新定義以本次實際插入的音訊為準，不等同第 2.3 節歷史實驗中以原始 MP3 產生的版本。initial 與校正版應共用定位結果，不重複匯出影片或各自重新定位；校正沿用既有時間模型，不對已校正字幕重複乘係數。

建議沿用 `--subtitles-output output/captions.srt`，在同目錄由檔名主體衍生 `_preview.srt` 與 `_initial.srt`；例如 `lesson.srt` 對應 `lesson_preview.srt`、`lesson_initial.srt`。三個路徑必須分開，匯出後不可覆蓋預測版或 initial。三份輸出亦適用補秒為 0 的完整匯出流程；這是字幕產物保留策略的調整，不改變原音訊處理方式。

匯出或定位失敗時應明確回報，不能把預測版冒充 initial，或把前次殘留檔案列為本次成功產物。若沿用既有定位退回機制，需在執行摘要標示退回頁面。完成摘要列出本次產物路徑、校正係數及定位異常，供人工比對。

### 6.2 人工確認與第二階段

使用者以同一份 MP4 掛載候選 SRT，核對前、中、後段及長頁面的頁首、頁尾，再選定字幕。`captions.srt` 的檔名不代表它必然最準；initial 已同步時可直接使用 initial，不必改名或為乘上 1.0 重建。

第二階段沿用獨立的 `scripts/burn_subtitles.py`，由使用者透過 `--srt` 明確選檔。此階段只需要影片與選定字幕，不重跑 TTS、音訊準備、PowerPoint 匯出或字幕校正；依第 12 節讀取實際影片尺寸，自動套用黑條參數，輸出至不同 MP4 路徑。

## 8. 字幕時間模型與尾端 anchor 風險

### 8.1 最小整合方案

沿用目前實驗方法，以衍生 M4A 同時供插入、預測長度與影片定位。音檔長度包含新增靜音，因此不再另外替頁面加 padding。

字幕文字與 WordBoundary 仍來自原始 TTS。新增停留不應被平均分配到語句，也不應讓最後一句自動顯示到換頁。

這個方案改動小，但需驗證 AAC 編碼延遲、音訊定位及頁內比例是否合理。不要因最後一句吻合就省略其他位置的測試。

### 8.2 必須處理的長停留限制

目前定位預設取末端 8 秒作為 anchor。加 4 秒後可能剩下少量有效語音；若追加接近或超過 8 秒，尾端模板可能幾乎全是靜音。

本次承諾的範圍為 1～10 秒，因此不能只驗證 4 秒；尾端定位保護列為必要工作，建議採用：

1. 根據準備 metadata，在新增靜音之前選擇有訊號的 anchor。
2. 保存 anchor 在來源音訊中的相對位置。
3. 由有效音訊對應關係推算頁內時間映射。
4. 將旁白區間與整頁媒體長度分開處理。
5. 低品質匹配或異常比例時回報，不能無條件採用相關峰值。

不能只將 anchor 向前移，卻仍把它的尾端當成整份音檔終點。這會使比例分子與分母代表不同區間。

可能涉及 `audio_position_locator.py` 與 `subtitle_pipeline.py` 的資料介面。需覆蓋 1、4、8、10 秒，以及短旁白或原本已有長靜音的案例；有效訊號不足時須明確回報或採取可追蹤的退回策略。未完成這些保護與驗收前，不能將 1～10 秒標示為正式支援。

### 8.3 Anchor 選取與座標處理

以下為採用的設計方向，尚未實作或完成可靠度驗證。尾端 anchor 以 8 秒為目標長度，先避開新增靜音，再檢查原始音訊區間是否具有足夠訊號；不是保證任何頁面都有 8 秒可用語音。

例如原始音訊 30 秒、追加 4 秒，直接取衍生音訊末端 8 秒會取得第 26～34 秒；新方法先選第 22～30 秒。若原始尾端也有靜音，需再往前尋找有效片段；若原始音訊不足 8 秒，採較短片段。不得用補零湊足長度，或把純靜音當成可靠模板。短音訊的頁首、頁尾片段若重疊或相距過近，也不能視為足夠獨立的兩個比例估計依據。

選取範圍須依 metadata 與解碼後實際訊號核對，不僅用容器時長減去補秒值。AAC 延遲或封裝差異仍需測試；來源 WordBoundary、衍生音訊與影片間的座標必須一致。記錄每個 anchor 的相對起點、長度及影片匹配位置。

若兩個可靠匹配點在音訊中的位置為 s1、s2，在影片中的位置為 v1、v2，可用相同參考點計算：

```text
scale = (v2 - v1) / (s2 - s1)
video_time(s) = v1 + (s - s1) × scale
```

此為時間映射概念；兩端需使用一致的匹配參考位置，並檢查間距及比例合理性。第 30 秒的匹配點不能被當成完整媒體第 34 秒的終點。旁白字幕依映射定位，完整媒體長度則保留新增靜音，供後續頁面預測使用；不得重複追加補秒。

可靠度判斷需綜合有效訊號量、匹配峰值與其他候選的差距、搜尋範圍、頁面順序及比例合理性；單一最高相關峰值不足以代表成功。門檻與搜尋次數上限由測試決定，第一版不要求使用者選數字或新增 anchor 調校 CLI。

### 8.4 找不到可靠 anchor 的處理政策

採用「保留影片與可用候選字幕、明確揭露退回頁面、交由人工確認」政策，不因單頁定位失敗重跑影片，也不自動進入燒字幕。但若結果違反時間基本條件，停止提交有問題的實測字幕。

| 狀況 | 處理方式 | 剩餘風險 |
|---|---|---|
| 頁首與尾端皆可靠，間距與比例合理 | 使用兩點估計頁內時間映射 | 仍需抽查，重複語句可能形成錯誤候選 |
| 頁首可靠、尾端失敗或無法可靠估比例 | 保留頁首匹配，頁內比例暫採 1.0，標示退回 | 開頭可同步，長旁白後段仍可能偏移 |
| 頁首不可靠，或沒有可用 anchor | 第一版退回該頁預測起點及比例 1.0；僅尾端可靠也不據此標示整頁成功 | 整頁可能提早或延後，必須人工核對 |
| 候選模糊、比例異常或訊號不足 | 拒絕可疑匹配，依可用的可靠頁首或預測值退回 | 失去部分實測保證，但避免採用已知可疑定位 |
| 退回後仍有時間倒退、零／負時長、超出影片範圍或非預期跨頁重疊 | 不提交受影響的整份 initial／captions；保留 MP4、preview 與診斷結果，回報字幕生成失敗 | 使用者需排查或重新產生字幕，不能將部分檔案當成完整成功產物 |

表中的比例 1.0 指退回頁面的頁內映射；initial 的額外全域校正仍為 1.0，captions 仍依明確指定的全域係數產生。兩種比例不得混淆，也不得以全域校正掩蓋單頁定位失敗。initial 有退回頁面時是「含預測退回的候選版」，不能宣稱整份皆已實測對齊。

輸出前分別驗證 initial 與校正版；某一版本不合法時不提交該版本，不必丟棄另一份合法候選。寫入採暫存後提交，失敗不覆寫前次有效檔案；摘要須清楚區分本次成功產物與前次殘留檔案。合法的預測退回可以完成第一階段，但須顯示需人工檢查的狀態；結構不合法則明確回報失敗。

### 8.5 影響範圍與錯誤傳播控制

- **原始音訊與 MP4**：anchor 分析在匯出之後執行，不修改已匯出的聲音或畫面。定位失敗本身不會造成缺字、斷音；若影片本身有問題，仍須另查音訊或 PowerPoint 匯出。
- **當頁字幕**：只有尾端失敗時主要失去比例估計；頁首失敗時可能整頁位移。即使時間順序合法，也不能證明與語音同步。
- **後續頁面**：當頁失敗不必然污染後續頁。後續頁應重新獨立定位；不得把遭拒絕的匹配作為下一頁的確定搜尋基準。連續退回預測時，匯出與預測差異可能累積，需標示整段受影響頁碼。
- **預測與搜尋**：保留完整媒體長度（含補秒）推算預測位置，區分可靠實測與預測值；重新取得可靠定位後可恢復實測對齊。有限範圍的擴大搜尋仍失敗時採退回，不無限制尋找相關峰值。
- **分段與診斷工具**：若使用同一批定位結果作影片切點，也會受到定位不確定性影響。須傳遞退回狀態，不能將預測音訊起點直接宣稱為精確畫面換頁點。

### 8.6 診斷產物、代價與驗收

建議隨字幕輸出結構化診斷檔，例如 `captions_alignment_report.json`，由 `--subtitles-output` 的檔名主體衍生。記錄本次影片與音訊來源識別、各候選字幕生成狀態及全域係數；逐頁記錄 anchor 範圍、匹配品質、採用的起點與比例、退回原因，以及建議人工檢查的影片時間區間。CLI 摘要列出可靠／退回／失敗頁數與頁碼，不只輸出難以解讀的相關分數。SRT 內容維持正常字幕，不插入診斷文字。

| 代價 | 控制方式與評估 |
|---|---|
| 額外解碼、訊號檢查與候選搜尋時間 | 共用解碼及定位結果、限制候選數與搜尋次數；量測大型簡報增加的耗時，不預先承諾固定比例 |
| 更多 metadata、狀態與座標傳遞邏輯 | locator 回傳明確狀態，pipeline 與獨立工具共用；增加短音訊、靜音、重複語句與連續失敗測試 |
| 人工檢查成本 | 提供頁碼與時間區間以集中檢查；仍抽查可靠頁面，避免完全依賴演算法自評 |
| 退回後同步精度下降 | 保留候選可供檢查，但不承諾最大偏差；量測可靠頁與退回頁各自的時間誤差 |
| 診斷檔及多份字幕的管理成本 | 統一命名並記錄生成批次／來源，避免把舊字幕搭配新影片；影片不因診斷另複製 |
| 字幕生成失敗後需要重試 | 保留影片及來源資料，使用既有重建入口重做定位／字幕，無須重跑 TTS 或 PowerPoint，除非媒體本身需改動 |

預期改善的是純靜音或錯誤 anchor 被當成可靠結果的風險，以及問題的可追查性，不保證所有頁面都能取得 anchor。驗收需包含：純靜音不判成功、短音訊不強行估比例、連續失敗不傳播可疑匹配、後續可靠頁可恢復、異常字幕不提交、診斷與實際產物一致；另以獨立人工標記量測誤判、退回率與字幕誤差。

### 8.7 獨立工具的相容性

既有 `regenerate_srt_from_export.py`、`split_video_by_slides.py` 可透過 prepared manifest 與目錄取得衍生音訊。若底層定位開始使用新增 metadata，這些入口應沿用共用讀取邏輯，不各自實作補秒規則。

無旁白頁時長仍由原本參數指定。音訊起點也不必然等於畫面轉場邊界，分段結果需實際檢查。

## 10. 測試與驗收

### 10.1 自動化測試

| 項目 | 驗證目的 |
|---|---|
| 不加新參數或明確指定 0 | 舊流程行為不變，不啟動轉換或自動選用殘留衍生產物 |
| 0 搭配明確 prepared 設定／強制重建 | 明確報錯；未明確指定的預設值不造成誤判 |
| 非法補秒與格式參數組合 | 拒絕超出範圍、非有限數值及 WAV 明確指定 AAC bitrate |
| 既有 manifest 單獨準備 | 不重新呼叫 Edge-TTS |
| M4A／WAV 與 1／4／8／10 秒、範圍內小數秒 | 格式、可解碼性、長度與尾端定位符合預期 |
| 來源與輸出目錄相同或互相包含 | 在寫入前拒絕，不搬移或覆寫原始資料 |
| 原始檔案雜湊 | MP3、WordBoundary 與原始 manifest 不被修改 |
| 相同設定重跑 | 重用產物，不累加靜音 |
| 原始檔／WordBoundary／設定變更 | 正確失效與重建，不混用舊資料 |
| 部分頁面重生 | 其餘頁面保留且仍可使用 |
| ffmpeg 不存在、轉換失敗、輸出不可讀 | 明確錯誤，不繼續插入 |
| 中途失敗 | 正式 manifest 不指向半套或混批次產物 |
| effective 資料串接 | payload、插入、定位與字幕使用相同來源 |
| 三份字幕與自訂輸出檔名 | preview、initial、校正版各自保留，命名正確且不互相覆蓋 |
| 預測與校正相依性 | preview 累計補秒；initial 固定係數 1.0；係數 1.0 時 captions 與 initial 一致，非 1.0 不重複校正 |
| 第一階段完成或失敗 | 不自動燒字幕；失敗不冒充實測產物，不將前次殘留檔當成本次成功結果 |
| 第二階段指定候選字幕 | 使用指定 SRT，不自動替換版本，不呼叫 TTS／PowerPoint／字幕重建 |
| 無旁白頁 | 不重複追加靜音，保留預設頁面時長 |
| 短音訊、長停留、靜音尾端 | 檢查定位退回與異常結果 |
| 頁首／尾端失敗與連續退回 | 驗證第 8.4 節各分支；可疑匹配不傳播，後續可靠頁可恢復 |
| 字幕時間不合法與診斷輸出 | 不提交異常版本，保留影片；頁碼、原因、來源及本次產物狀態一致 |

可用合成音訊建立已知時間位置的驗證資料；有 ffmpeg 的測試需实际檢查輸出，不能全靠 mock。缺少 ffmpeg 時應明確跳過相應整合測試。

### 10.2 真實 PowerPoint 驗收

假的 COM 物件只能驗證呼叫參數，不能證明沒有斷字。保留曾缺少「行」發音的案例作人工或可重複媒體對照，記錄 PowerPoint、Windows、FFmpeg 版本。

使用 `sample_test.pptx` 與大型 `MPU_WK01.pptx` 分別檢查：

- 旁白內容完整，沒有固定位置缺音或异常停頓。
- 影片中音訊播放結束至換頁的額外停留符合設定；區分原有尾端靜音與新增部分。
- 前、中、後段，以及各長頁面的頁首與頁尾字幕同步。
- 不出現新增零時長、時間倒退或跨頁重疊。
- 不因 prepared 音訊而新增定位失敗或不合理頁內比例。
- 最後一頁、無旁白頁與動畫頁符合預期。

大型簡報以 4 秒 M4A 作主要回歸基準；範例簡報另需驗收 1、8、10 秒與 WAV 對照，尤其檢查尾端 anchor 落入靜音時的定位與字幕結果。

### 10.3 評估指標

- 轉換後音訊時長增量與設定差值。
- 人工核對字幕時間誤差的 P50、P95、最大值。
- 定位失敗頁數、退回預測頁數、異常比例頁數。
- 重複執行新增處理量與來源不一致攔截率。
- 音訊、PPTX、MP4 檔案大小及各階段耗時。
- 失敗後是否保有完整原始資料與前一份有效 prepared manifest。

首輪先建立現行實驗的基準，不預先宣稱某個百分比的可靠度提升。使用與定位演算法獨立的播放核對，避免只靠同一方法驗證自身。

## 11. 建議實作順序與範圍

1. 新增準備模組、錯誤類別、manifest metadata 與安全提交。
2. 接上以補秒為唯一開關的 CLI 與 effective 資料流，驗證 0 的原音訊行為及衝突處理；明確劃分第一階段與獨立燒錄入口。
3. 完成尾端 anchor 保護、metadata 傳遞與一致的頁內時間映射，涵蓋 1～10 秒。
4. 完成三份候選字幕保留與摘要，加入轉換、重跑、失敗、完整補秒範圍及兩階段 CLI 整合測試。
5. 以 4 秒 M4A 完成大型簡報驗收，並完成範例簡報的邊界秒數與 WAV 對照；未通過時不標示為正式可交付。
6. 人工確認選定字幕後，以第二階段驗收第 12 節的黑條自動縮放，覆蓋 720p、1080p 與手動覆寫。
7. 更新使用文件與實驗紀錄；超過 10 秒或只轉格式屬於後續另行評估的範圍。

本次不綁定處理其他獨立議題：現場放映自動播放、已插入媒體的辨識與替換、PowerPoint COM 逾時機制重設、全套字幕可信度系統或任意 ffmpeg 參數透傳。這些可獨立規劃；目前仍要求從乾淨原始 PPTX 生成含音訊版本。

## 12. 追加需求：依影片解析度自動縮放字幕黑條

### 12.1 實驗結果與適用範圍

使用者確認：720p 改為 1080p 後，文字大小看起來正常，但黑條變得相對較小。將黑條寬、高及底部位置參數放大 1.5 倍，保留原有字級與文字邊距，以前 5 分鐘影片預覽後，使用者確認字幕底色正確。

因此將自動縮放納入本次修改評估。這是已確認的樣式需求，尚未寫入程式。已驗證情境為同一投影片比例與樣式的 1280×720／1920×1080；其他比例、旋轉影片及非方形像素不宣稱已驗證。

| 設定 | 720p | 1080p |
|---|---:|---:|
| 黑條寬度 `bar_width_px` | 650 | 975 |
| 黑條高度 `bar_height_px` | 38 | 57 |
| 畫面底部至黑條頂邊 `bar_bottom_offset_px` | 40 | 60 |
| 字級 `font_size` | 15 | 15 |
| 文字垂直邊距 `margin_v` | 1 | 1 |

黑條底邊距畫面底部，分別為 `40−38=2 px` 與 `60−57=3 px`。水平位置維持置中，由現有 `(iw-width)/2` 計算，不需要另加水平偏移。

### 12.2 自動判斷與縮放公式

燒字幕階段使用 ffprobe 讀取實際輸入 MP4 的視訊尺寸，不依賴前一次匯出 CLI 的 `--video-resolution`，也不從檔名推測。獨立燒字幕與分段燒字幕必須共用同一份邏輯。

對已支援的標準橫向影片，以 720p 為基準：

```text
scale = video_height / 720
bar_width = round(650 × scale)
bar_height = round(38 × scale)
bar_bottom_offset = round(40 × scale)
```

第一版必須驗收 1280×720 與 1920×1080。若延伸至其他解析度，應檢查畫面比例及尺寸合法性；無法套用已驗證基準的情境需明確提示使用手動值或 fixed 模式，不能靜默聲稱版面相同。

不要將 `FontSize` 與 `MarginV` 一起乘倍率。現行程式透過 libass 的 ASS 樣式渲染文字，其座標與輸出像素不是相同概念；相同比例與渲染設定下，保留原值可維持本次已確認的文字效果。現有 CLI 將字級與 MarginV 簡稱為 px 的說明也應修正。

### 12.3 CLI 與優先順序

建議在 `scripts/burn_subtitles.py` 與分段燒字幕入口新增：

| 參數 | 建議預設 | 用途 |
|---|---|---|
| `--bar-scale-mode` | `auto` | `auto` 依實際解析度換算；`fixed` 使用原本固定像素預設 |

保留既有 `--bar-width`、`--bar-height`、`--bar-bottom-offset`，明確指定時視為最終輸出像素，不再縮放。參數解析預設改成 `None` 以辨識是否手動指定，原本 650／38／40 保留為基準常數。

每個幾何參數獨立解析：

1. 有明確 CLI 值：直接使用該值。
2. 未指定且為 auto：採用解析度換算值。
3. 未指定且為 fixed：使用原本 720p 基準值。

例如在 1080p 明確給 `--bar-width 900`，最後採用寬 900、高 57、offset 60，不會再將 900 乘 1.5。所有解析後值都應檢查正值、黑條是否超出畫面，以及高度與底部位置是否合理。

預設 auto 會有意改變「1080p 且未指定黑條尺寸」的既有行為；720p 保持原樣。需要重現舊固定尺寸時，可使用 fixed 模式。文件與 CHANGELOG 必須記錄這項相容性差異。

### 12.5 驗收

- 720p 未指定參數時，得到 650／38／40，與舊樣式一致。
- 1080p 未指定參數時，得到 975／57／60。
- 字型、FontSize=15、MarginV=1 不額外乘倍率。
- 手動值只套用一次；支援部分覆寫與完整覆寫。
- fixed 模式保留原本固定像素效果。
- 完整影片與分段影片燒字幕使用相同縮放邏輯。
- ffprobe 失敗或不支援的影片幾何明確回報，不猜測解析度；完整手動值／fixed 模式可按設計提供不依赖自動縮放的路徑。
- 用合成 720p／1080p 影片与相同字幕確認黑條幾何；以真實字幕預覽確認長句不超出黑條、頁尾不被非預期遮擋。

可先用短片驗證樣式再燒整片，無須重跑 TTS、音訊準備或 PowerPoint 匯出。新增預覽時長 CLI 不是此次自動縮放的必要條件，暫不列入實作範圍。
